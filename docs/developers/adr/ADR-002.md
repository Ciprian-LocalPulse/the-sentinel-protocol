# ADR-002: Local-First Reference Implementation Before a Hosted Service

**Status:** Accepted
**Date:** 2026-07-31

## Context

The whitepaper described a fully deployed, always-on system (private
server, vector store, n8n/Make orchestration loops) from the start. This
repository's Phase 4 needed to decide whether to build toward that
end-state directly or start smaller.

## Decision

Build a local-first reference implementation
(`prototype/python/`, `docs/deployment/local.md`) with a FastAPI service
(`prototype/python/api/server.py`) runnable on a single machine, before
specifying the containerized (`docker.md`) or multi-user cloud
(`cloud.md`) deployment targets.

## Consequences

- **Positive:** Every core algorithm (scoring, leverage, capacity,
  encryption) has test coverage runnable in CI with zero external
  infrastructure — see `.github/workflows/tests.yml`. This makes the
  architecture easy to verify and easy for a new contributor to run.
- **Positive:** The Iron Vault's local-only master key requirement
  (`docs/security/encryption.md`) is trivial to honor when the default
  posture is already local-first.
- **Negative:** Multi-user/team features (`docs/deployment/cloud.md`)
  remain unimplemented pending real demand, per
  `docs/design-principles.md` §7 ("simple first, elastic later").

## Alternatives Considered

- **Build the full n8n/Make orchestration layer first.** Rejected —
  couples the reference implementation to a specific third-party
  automation platform before the core logic is even validated.
